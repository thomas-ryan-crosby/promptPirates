Research & whitepapers

Procedural Graphs: Self-Evolving Execution Structures for LLM Agents Advanced

Current approaches to agent memory store raw facts or past trajectories; this paper asks whether agents could instead maintain and refine an explicit map of how to act. A Procedural Graph organizes procedural knowledge as (procedure, relation, procedure) triplets—capturing what to do and in what order—in the same way a knowledge graph organizes (entity, relation, entity) facts. At each decision step, a guidance model localizes the active node and translates the surrounding subgraph into situational step-level guidance that biases the solver’s next action without hard-coding it. What makes the approach practical is the self-evolution loop: an LLM refiner contrasts failed trajectories with successful ones and edits the graph’s topology and attributes, committing edits that preserve or improve held-out validation performance while retaining rejected ones to discourage repetition. Across multiple datasets, task types, and LLMs, Procedural Graphs deliver consistent gains over memory-only baselines, and self-evolution adds a further performance lift without manual engineering. For teams building agents that repeat structured multi-step workflows, this is a concrete alternative to appending raw history.

When Passing Tests Hides Vulnerabilities: An Empirical Study of Silent Failures in Agentic Systems Advanced

Agentic code repair pipelines typically gate on a patch passing the repository’s existing test suite. This paper from Tampere University asks what lies beneath that signal. Across 1,030 valid execution traces produced by seven agent frameworks with GPT-4o-mini on SecurityEval and CVEfixes, the authors identify 170 confirmed silent failures: patches that pass syntactic and functional verification but still retain or introduce security vulnerabilities. Three categories account for all cases—Omission (agent fixes the non-vulnerable surface but leaves the root cause in place, 48.2%), Introduction (agent adds a new vulnerability while patching the reported one, 30.6%), and Inadequacy (patch is incomplete or shallow and leaves a residual attack surface, 21.2%). Critically, neither test-passing evaluation nor an LLM-based reviewer role reliably caught these failures in the confirmed cases. For practitioners running agentic code repair: the passing-tests signal is not a security signal, and the paper’s taxonomy is a practical checklist for designing the verification step that actually needs to follow patch generation.

Releases & tooling

Gemini 3.8 Flash and 3.8 Flash Cyber Intermediate

Released September 2 as Google’s most intelligent Flash model, Gemini 3.8 Flash is designed for long-horizon software engineering and autonomous agents at Flash speed and cost. The model accepts text, image, video, audio, and PDF input; returns text; offers a 1-million-token context window with a 64K-token output limit; and reasons by default at a configurable low, medium, or high thinking level. The engineering gains over 3.7 Flash are sharpest on coding and agent benchmarks: DeepSWE v1.1 climbs from 65.3 to 73.7 percent and Terminal-Bench scores rise significantly as well. Pricing stays at the same introductory rate as 3.7 Flash ($0.75/$3.75 per million tokens through December 2026), making the performance jump essentially free. A companion model, Gemini 3.8 Flash Cyber, ships with a more permissive mitigation set and frontier-level performance on CyberGym for autonomous vulnerability discovery; it is available to trusted defenders through Google’s Fairwind Program, bundled with the CodeMender harness for agentic find-verify-fix workflows. The model ID for general use is gemini-3.8-flash.

OpenAI Agents API enters public beta Intermediate

On September 10, OpenAI opened its Agents API to all developers in public beta, extracting the orchestration layer it built for Codex into a standalone API that any application can call. The API manages long-running agent sessions, handles context compaction automatically as a session approaches its token limit, recovers from failures, and coordinates sub-agents—none of which the developer needs to implement themselves. Agents stream progress back to the application as they run, and sessions can use OpenAI-hosted sandboxes or a developer-provided compute environment. The API supports MCP and custom tools and includes configurable rollout token budgets to track usage across agent threads and abort turns when exhausted. There is no additional fee: developers pay for the tokens and tools their agents consume. For teams that have been hand-rolling context compaction, session recovery, and multi-agent coordination in their own infrastructure, this is the managed alternative that brings those concerns off the hot path. The full Codex feature set—including cross-context-window notes and searchable earlier sessions—is also available when the API is used through Codex.

OpenAI · September 10, 2026

Claude Managed Agents: auto permission policy and ant beta:sessions connect Intermediate

Two additions landed September 10 for the Claude Managed Agents API. The first is the auto permission policy, a third option alongside always_allow and always_ask: when set, the server evaluates each agent or MCP tool call in the context of the session’s full history and the call’s input, then runs it, denies it, or pauses for your approval. The evaluation is per-call, so two invocations of the same tool in the same session can receive different outcomes depending on what the agent is trying to do. High-risk calls—such as rm -rf operations on workspace directories—are denied outright and cannot be overridden by your client. The second addition is ant beta:sessions connect, which attaches the terminal to any running session, displays the live transcript with timing and outcomes, and changes the input line to an approval prompt when a tool call is waiting. It also takes a --web flag to serve the Claude Console’s session viewer locally. Together these two features address the two modes of agent supervision: auto handles the known-safe majority without friction, and sessions connect provides an immediate human-in-the-loop path for anything the server flags as uncertain. Documentation: permission-policies and sessions-connect.

Claude Code v2.1.265–270: plugin evals, output-style switching, effort caps, Bash diffs Intermediate

Six versions shipped September 8–12. The headline addition in v2.1.269 is claude plugin eval—a command that runs a plugin’s eval suite against Claude Code and produces a scored, reproducible JSON-plus-HTML report, giving plugin authors a first-class way to measure and regression-test behavior. Also in v2.1.269: /output-style [name] lists and switches output styles including in cloud and headless sessions, a diff of files changed by a Bash command is appended to the Bash tool result, and the VS Code extension gains an agent map showing each sub-agent with per-agent cards and read-only transcripts. v2.1.267 adds maxEffortLevel (top-level or per model under modelSettings) to cap the per-request effort ceiling on every provider including Bedrock, Vertex, and Foundry—a useful cost control for organizations running workloads across multiple backends. The same version adds --system-prompt-snapshot off to render the system prompt fresh on every request rather than reusing the conversation’s initial snapshot. v2.1.268 fixes a compatibility regression affecting all third-party Anthropic-compatible endpoints since 2.1.265 (HTTP 400 on every turn), and fixes WebFetch hanging indefinitely on slow servers by capping fetches at 300 seconds.

Benchmarks & evals

ττ-Bench: An Environment for End-To-End, Realistic Agent Construction Advanced

Most agent benchmarks hand an agent a task and ask it to complete it. ττ-Bench, submitted to arXiv September 4, makes building the agent the task. A developer agent receives business records, client requirements, a production API, a codebase to inherit, and cost and model constraints; it must deliver a complete customer-service agent, which is then scored by deploying that agent against held-out simulated users. The 53 tasks span four domains and require the developer agent to interpret underspecified business requirements, choose appropriate tools, and produce an agent that generalizes beyond the example cases it was shown—without asking a human for clarification at any point. The benchmark’s main finding is sobering: across all configurations tested, the best result was Claude Opus 5 under Claude Code at 23.9 percent, against an expert-authored reference ceiling of 82.2 percent. The gap is not primarily explained by coding skill—the developer agents write syntactically valid code—but by failures in requirement interpretation, constraint adherence, and instruction-following under held-out user behavior. For teams evaluating agentic platforms on downstream usefulness rather than code generation, this benchmark captures a real dimension that SWE-bench-style scores do not.

Back to the deck The two research papers this week reinforce each other in an uncomfortable way: one shows that agents cannot yet reliably construct agents, and the other shows that when agents do write code, the standard pass-gate misses a meaningful share of security failures. Neither result is surprising on its own, but together they point to the same gap—the evaluation layer between agent output and declared success is still underbuilt. The infrastructure news runs the opposite current: both OpenAI and Anthropic shipped managed session orchestration this week, which means the plumbing for long-running supervised agents is now a commodity rather than a home-rolled system. The interesting work is shifting to what runs on top of that plumbing, and to whether the signals we use to know it worked are worth trusting.
